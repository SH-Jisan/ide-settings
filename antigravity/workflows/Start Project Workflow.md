\# Start Project Workflow



\## Step 1: Understand the Project



Understand the project's actual purpose before designing or implementing anything.



Identify:



\* the problem being solved,

\* target users,

\* primary use cases,

\* expected outcomes,

\* functional requirements,

\* non-functional requirements,

\* constraints,

\* available resources,

\* expected scale,

\* security requirements,

\* performance requirements,

\* and important success criteria.



Ask for clarification when missing information could materially affect the project.



Do not begin significant implementation before the core project goal is sufficiently understood.



\## Step 2: Analyze the Problem and Context



Analyze the project from a professional engineering perspective.



Consider:



\* the real-world problem,

\* existing alternatives,

\* project complexity,

\* technical constraints,

\* likely risks,

\* dependencies,

\* scalability needs,

\* maintainability,

\* reliability,

\* security boundaries,

\* and future expansion.



Identify unnecessary complexity early.



\## Step 3: Research When Needed



Research current and relevant information when it could materially improve important technical decisions.



Prefer:



\* official documentation,

\* authoritative standards,

\* maintained technologies,

\* reliable engineering resources,

\* and current ecosystem guidance.



Research areas such as:



\* technology choices,

\* frameworks,

\* libraries,

\* architecture patterns,

\* security practices,

\* compatibility,

\* APIs,

\* and current best practices.



Do not research unnecessarily when the information is stable and sufficient knowledge already exists.



\## Step 4: Evaluate Approaches



Identify meaningful solution approaches.



Compare important alternatives based on:



\* project requirements,

\* implementation complexity,

\* maintainability,

\* scalability,

\* security,

\* performance,

\* reliability,

\* developer productivity,

\* ecosystem support,

\* long-term sustainability,

\* and compatibility.



Recommend the approach that best fits the actual project rather than automatically choosing the newest or most popular technology.



Explain important trade-offs.



\## Step 5: Define the System



Before major implementation, define an appropriate system design.



Consider:



\* major components,

\* responsibilities,

\* data flow,

\* system boundaries,

\* interfaces,

\* APIs,

\* databases or storage,

\* authentication,

\* authorization,

\* security boundaries,

\* external services,

\* deployment,

\* observability,

\* and scalability where relevant.



Keep the architecture proportional to the project.



\## Step 6: Define the Technology Stack



Recommend an appropriate technology stack.



For significant technology choices, explain:



\* why the technology is suitable,

\* what problem it solves,

\* important advantages,

\* important limitations,

\* alternatives considered,

\* compatibility,

\* and project impact.



Do not introduce significant technologies or dependencies without clear value.



Obtain user approval when appropriate before introducing major technologies or architectural dependencies.



\## Step 7: Create Project Structure



Design a professional project structure appropriate to the technology and project size.



Create or plan:



\* source directories,

\* configuration,

\* tests,

\* documentation,

\* environment configuration,

\* build or deployment structure,

\* and other relevant project directories.



When appropriate, create:



\* `docs/` for project documentation,

\* `ide/` for project planning, implementation notes, important decisions, and development logs.



Do not create unnecessary structure for trivial projects.



\## Step 8: Create Documentation



Create appropriate project documentation when useful.



Possible documents include:



\* project overview,

\* requirements,

\* architecture,

\* technology decisions,

\* API design,

\* database design,

\* security considerations,

\* implementation plan,

\* testing strategy,

\* and deployment plan.



Keep documentation useful, concise, and aligned with the actual project.



\## Step 9: Create Project-Specific Rules and Workflows



Analyze whether project-specific Workspace Rules or Workflows would meaningfully improve consistency, quality, efficiency, maintainability, or development speed.



When appropriate:



\* create Workspace Rules for persistent project conventions and requirements,

\* create technology-specific Rules,

\* create architecture or security Rules,

\* create testing or documentation Rules,

\* create Workflows for recurring project processes.



Avoid duplicating Global Rules.



Avoid creating unnecessary Rules or Workflows for one-time or trivial tasks.



\## Step 10: Create the Implementation Roadmap



Break the project into logical implementation phases.



For each phase, identify:



\* objectives,

\* affected components,

\* dependencies,

\* major tasks,

\* verification requirements,

\* and important risks.



Define a sensible implementation order.



\## Step 11: Present the Project Plan



Before major implementation, provide a clear summary of:



\* project understanding,

\* recommended solution,

\* architecture,

\* technology stack,

\* project structure,

\* major implementation phases,

\* important trade-offs,

\* risks,

\* and recommended next steps.



Clearly distinguish confirmed decisions, assumptions, and recommendations.



Do not claim implementation has started or verification has occurred unless it actually has.
